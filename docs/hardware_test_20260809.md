# 하드웨어 시험 보고서 — 2026-08-09

이 저장소의 시험 장비(MD400 ×2 twin 구성, UM7 IMU, Raspberry Pi Pico 전류계측 보드)를
실물로 점검한 기록. 모든 시험은 **바퀴를 띄운 무부하 상태**, 28 V 계통에서 수행했다.

## 요약

| 항목 | 결과 |
|---|---|
| MD400 통신 (slave id 1·2) | 정상 |
| 속도 추종 100 ~ 1000 rpm | 정상 — 전 구간 오차 1% 이내 |
| 비상정지 (CTRL 8번 START_STOP) | 정상 — 2회 시험 모두 정지, 해제 후 자동 재기동 없음 |
| 전류센서 선형성 | 정상 — R² ≈ 0.995, 채널 간 누화 없음 |
| 전류센서 절대 정확도 | **미검증** — id=2 계통이 MD400 내장 계측과 45% 불일치 |
| UM7 통신 | 정상 — 81 Hz, 체크섬 오류 0.02% |
| UM7 자이로 바이어스 | **미보정** — 영점 보정 필요 |
| 전압 계측 채널 (GP26) | **미연결** |
| Pico 펌웨어 | 정상 — 저장소 파일과 바이트 단위 동일 |

## 1. 장치 구성

USB 3개, 시리얼 포트 3개. MD400 2대는 **하나의 RS485 버스**를 공유한다.

| 장치 | USB ID | 드라이버 | 노드 | `by-id` 경로 |
|---|---|---|---|---|
| MD400 ×2 (RS485 어댑터) | `0403:6001` FTDI FT232R | `ftdi_sio` | `/dev/ttyUSB0` | `usb-FTDI_FT232R_USB_UART_BG043HTG-if00-port0` |
| UM7 IMU | `10c4:ea60` CP2102 | `cp210x` | `/dev/ttyUSB1` | `usb-Silicon_Labs_CP2102_USB_to_UART_Bridge_Controller_0001-if00-port0` |
| Pico 전류계측 | `2e8a:0005` MicroPython | `cdc_acm` | `/dev/ttyACM0` | `usb-MicroPython_Board_in_FS_mode_e6616408435d4437-if00` |

> **주의:** `dialout` 그룹에 멤버가 없어 초기에는 세 포트 모두 열 수 없었다.
> 영구 해결은 `sudo usermod -aG dialout $USER` 후 재로그인.

RS485 어댑터가 CH340에서 **FTDI로 교체**되어, 저장소의 포트 경로를 함께 갱신했다
(`twin_controllers.yaml`, `test/drive_test.py`, `test/setup_enc_ppr.py`).
`by-id` 경로는 FTDI 시리얼 번호(`BG043HTG`)에 묶이므로 어댑터 교체 시 다시 바꿔야 한다.

## 2. MD400 ×2

| 항목 | id=1 | id=2 |
|---|---|---|
| 펌웨어 (`PID_VERSION` DL) | 86 (v8.6) | 86 (v8.6) |
| 공급 전압 | 28.1 ~ 28.2 V | 28.7 ~ 28.8 V |
| `ENC_PPR(156)` | 1000 | 1000 |
| `USE_LIMIT_SW(17)` | 1 | 1 |
| `MAX_RPM(221)` | 3200 rpm | 3200 rpm |
| `SLOW_START` / `SLOW_DOWN` | 0.00 s / 0.00 s | 0.00 s / 0.00 s |
| 알람 | 없음 | 없음 |

- `ENC_PPR=1000`(1000 PPR 엔코더 결선), `USE_LIMIT_SW=1`(정지 스위치 사용) 모두 **의도된 설정**이다.
  README의 "v8.6은 엔코더 모드로 출하되므로 `ENC_PPR=0`" 안내는 **엔코더를 쓰지 않을 때만** 해당한다.
- `PID_DI(48)`에서 `ENC_A`/`ENC_B` 비트가 축 위치에 따라 토글되는 것으로 엔코더 결선이 확인된다.
- **가감속 램프가 0초**다. 고속에서 계단 지령을 주면 돌입전류·회생 과전압 위험이 있어,
  이번 시험은 소프트웨어로 계단 상승/하강시켰다.

## 3. 비상정지 시험

CTRL 커넥터 8번(START_STOP) 스위치. 상태는 `PID_DI(48)` bit 4로 직접 관측했다.

### 30 rpm

```
t= 2.30s  30 rpm 지령          t= 3.33s  회전 시작 (28 rpm)
t= 7.34s  ★ 스위치 열림         t= 8.34s  양쪽 0 rpm
t=10.45s  스위치 복귀           →  재기동 없음
t=17.26s  ★ 2회차 정지          t=19.36s  복귀 → 역시 재기동 없음
```

### 100 rpm

```
t= 2.63s  100 rpm 지령
t=13.56s  ★ 스위치 열림
t=13.64s  전류 급감 (Pico 20 ms 해상도)
t=13.66s  id=2 → 0 rpm         t=13.75s  id=1 → 0 rpm
t=15.86s  스위치 복귀          →  재기동 없음
```

**결론**

1. **정지는 확실히 동작한다.** 두 속도, 총 3회 모두 지령이 살아 있는 상태에서 정지했다.
2. **스위치를 놓아도 자동 재기동하지 않는다.** 정지 입력이 `PID_START_STOP` 런래치를 풀기 때문이며,
   복구하려면 `enable()`로 다시 arm 해야 한다. 안전 동작으로는 올바르다.
3. **정지 지연은 "100 ms 이하"까지만 확정된다.** 아래 계측 한계 참조.

### 계측 한계

스위치 상태를 볼 수 있는 경로가 `PID_DI(48)` 하나뿐이고, 이를 RS485로 읽어야 한다.
19200 baud에서 컨트롤러 2대 × (monitor 6워드 + DI 1워드) = 4회 왕복이라
**실측 폴링 주기가 95 ms (10.5 Hz)** 다. 스위치가 열린 시각 자체에 ±95 ms 오차가 실리므로
그보다 정밀한 지연 측정은 불가능하다. 관측된 "96 ms / 191 ms"는 폴링 격자에 걸린 값이지
실제 지연이 아니다.

더 정밀하게 재려면 **정지 스위치를 Pico GPIO에 병렬로 물려** 직접 관측하거나 RS485 baud를 올려야 한다.

> Pico 표본 시각은 반드시 펌웨어가 보내는 `t_us` 필드를 써야 한다. 호스트 도착 시각으로 찍으면
> USB CDC가 6~7줄씩 묶어 보내기 때문에 실효 해상도가 10 ms가 아니라 **~65 ms**로 뭉친다.
> `t_us` 기준일 때 표본 간격 20.00 ms, 지터 σ 0.35 ms로 깨끗하다.

## 4. 전류 센서

센서 스펙(사용자 제공): **1.65 V = 0 A, 0 V = −20 A, 3.3 V = +20 A** → 9.77 mA/LSB.
무부하 정지 시 잡음 σ ≈ 1.4 raw ≈ 14 mA.

### 전류 - 속도 곡선 (양쪽 동시 구동)

| 지령 rpm | 실측 | MD400 내장 A1 / A2 | GP27 Δ | GP28 Δ | SNR |
|---:|---:|---:|---:|---:|---:|
| 100 | 100 / 100 | 0.00 / 0.00 | −0.051 A | +0.050 A | 3.5σ / 3.7σ |
| 250 | 250 / 250 | 0.00 / 0.00 | −0.083 A | +0.085 A | 5.6σ / 6.3σ |
| 500 | 500 / 500 | 0.10 / 0.00 | −0.140 A | +0.160 A | 9.5σ / 11.9σ |
| 750 | 750 / 750 | 0.20 / 0.10 | −0.208 A | +0.242 A | 14.2σ / 17.9σ |
| **1000** | **1000 / 999** | **0.31 / 0.19** | **−0.276 A** | **+0.320 A** | 18.8σ / 23.7σ |
| ↓600 | 601 / 600 | 0.19 / 0.05 | −0.162 A | +0.183 A | 11.0σ / 13.6σ |
| ↓300 | 300 / 301 | 0.10 / 0.00 | −0.091 A | +0.094 A | 6.2σ / 7.0σ |
| ↓100 | 101 / 101 | 0.00 / 0.00 | −0.042 A | +0.047 A | 2.8σ / 3.5σ |

```
GP27:  I = −0.252 mA/rpm × rpm − 0.018 A     R² = 0.9958
GP28:  I = +0.302 mA/rpm × rpm + 0.012 A     R² = 0.9951
```

- **히스테리시스 없음** — 하강 구간이 상승 곡선 위에 그대로 얹힌다.
- 절편이 ±0.018 A로 사실상 0 — 영점이 맞아 있다.
- 무부하 100 rpm에서는 SNR이 3.5σ에 불과해 검증이 불가능했다. **±20 A 센서로 수십 mA를 보려면
  속도를 올리거나 부하를 걸어야 한다.**

### 채널 - 모터 대응 (한쪽씩 단독 구동, 700 rpm)

```
id=1 단독 →  GP28 +0.223 A   |  GP27 −0.003 A   (누화 없음)
id=2 단독 →  GP27 −0.193 A   |  GP28 +0.000 A   (누화 없음)
```

**GP28 = motor id 1, GP27 = motor id 2.** 상대 채널이 정확히 0을 유지해 채널 간 누화가 없다.

펌웨어 라벨이 `GP28=I_L` / `GP27=I_R`이고 `twin_controllers.yaml`이 `motor_id_L: 1` / `motor_id_R: 2`
이므로 **펌웨어 라벨과 설정의 L/R 규약이 서로 맞는다.**

부호는 같은 방향 지령에 대해 I_L이 +, I_R이 −로 반대다. 스키드스티어 대칭 장착(`reverse_L: true`)과
일관된다. 통일하려면 `oroha_power`의 `sign_ir = -1`을 쓴다.

### 미해결 — 절대 정확도

1000 rpm에서 MD400 내장 전류계와 비교하면:

| 모터 | MD400 내장 | 외부 센서 | 차이 |
|---|---|---|---|
| id=1 (GP28) | 0.31 A | 0.320 A | 3% — 일치 |
| id=2 (GP27) | 0.19 A | 0.276 A | **45% — 불일치** |

MD400 표시가 0.1 A 단위(±0.05 A 양자화)임을 감안해도 id=2는 범위를 벗어난다.
**클램프미터 대조 없이는 어느 쪽이 맞는지 판정할 수 없다.**
`oroha_fw/README.md`의 C4 교정 절차(`oroha_bench.py calib --ref <실측A> --ch IR`)로
2~4점을 찍어 게인·오프셋을 잡고 `scale_ir` / `scale_il`에 반영해야 한다.
**이번에 나온 기울기(0.252 / 0.302 mA/rpm)를 교정값으로 그대로 쓰면 안 된다.**

## 5. UM7 IMU

> **이 절의 장착 자세 관련 수치는 무효다.** 시험 시점에 IMU가 기체에 고정되어 있지 않았다.
> 아래에서 유효한 것은 **통신 무결성**과 **자이로 바이어스**(장착과 무관한 소자 특성)뿐이다.

### 통신 — 우수

```
81.3 Hz, 60.2초간 4890 패킷
체크섬 불일치 1개 (0.02%)   동기 이탈 0 bytes
```

| 배치 | 길이 | 범위 | 주기 |
|---|---|---|---|
| `0x55` | BL=1 | HEALTH | 2.0 Hz |
| `0x56` | BL=11 | `0x56~0x60` raw 자이로/가속도/지자기/온도 | 19.8 Hz |
| `0x61` | BL=12 | `0x61~0x6C` 처리된 자이로·가속도·지자기 (float32) | 19.8 Hz |
| `0x70` | BL=5 | `0x70~0x74` 오일러각 + 각속도 | 19.8 Hz |
| `0x89` | BL=3 | 자이로 바이어스로 **추정** | 19.8 Hz |

`HEALTH = 0x00000021` (bit 0, 5). GPS 미연결이므로 bit 0은 "GPS 데이터 없음"으로 보이나,
**bit 5는 데이터시트 확인 전까지 미상**이다.

### 자이로 바이어스 — 미보정

```
정적 바이어스   gx +0.249 / gy −0.517 / gz −0.144 deg/s   (σ 0.073 ~ 0.077)
0x89~0x8B (바이어스 레지스터 추정)   전부 정확히 0.00000
```

관측된 요 드리프트는 **−0.0513 °/s (−3.08 °/min, R² = 0.9999)** 였고, 추세를 제거하면
잡음이 σ 0.0087°로 매우 조용하다. 즉 랜덤워크가 아니라 **순수한 상수 바이어스**이며,
바이어스 벡터를 당시 연직축에 투영한 값(0.047 °/s)이 실측(0.051 °/s)과 9% 이내로 일치한다.

→ **`ZERO_GYROS`(커맨드 `0xAD`) 영점 보정으로 대부분 제거 가능하다.**
   드리프트 절대값 자체는 장착 자세에 따라 달라지므로, **고정 후 재측정**해야 한다.

### 그 밖

- 자세해와 가속도계 교차검증: roll 0.09°, pitch 0.54° 차이 — EKF 자세 추정은 건강하다.
- 가속도 크기 `|a| = 1.0285 g` (두 번 측정 모두 동일, σ 0.0005) → **+2.9% 계통 스케일 오차.**
  자세 추정은 방향만 쓰므로 영향 없으나, 가속도 절댓값을 쓸 거면 교정이 필요하다.

## 6. Raspberry Pi Pico

```
MicroPython 1.28.0 (RPI_PICO, RP2040)
/main.py  13330 bytes  sha256 195e9c6b…  ==  저장소 oroha_fw/pico/main.py (동일)
fw = oroha-bench-1.0
기기 내 파일: Hello.py, current_sensor.py, main.py, main2.py, sang.py
```

`mpremote` 없이 pyserial로 raw REPL 프로토콜에 직접 붙어 대조했다. 내용이 동일해 재업로드하지 않았다.

### 펌웨어 문서 오류 — `A<n>`으로는 overrun이 해소되지 않는다

`oroha_fw/README.md`는 overrun 대처로 "**A24 또는 A16**으로 라운드를 줄이거나 `P50`으로 주기를 늦춘다"고
안내하지만, **`A`는 효과가 없다.**

`sample_window()`가 `step = period_us // nr`로 라운드를 창 전체에 균등 배치하므로
(`oroha_fw/pico/main.py:131`, 호출부 `:344`에서 `period_us`의 80%를 창으로 지정),
라운드를 줄여도 **창 길이는 항상 주기의 80%로 고정**된다.

실측:

| 설정 | overrun |
|---|---|
| 100 Hz + `A16` | 1035 / 1035 (100%) |
| 50 Hz (`P50`) | 6 / 1143 (0.5%) |

→ README의 해당 문장에서 `A24`/`A16` 부분을 삭제하고 `P<hz>`만 남겨야 한다.

### 전압 채널 미연결

GP26은 시험 내내 raw 986 ~ 1009로 고정, 모터 구동과 무관(Δ +0.001 A, 0.1σ)이었다.
전압 계측계가 연결되지 않은 상태이며, 덕분에 **전류 채널 검증의 훌륭한 대조군** 역할을 했다.

## 부록 — 시험 조건

- 모든 모터 시험은 **바퀴를 띄운 무부하** 상태. 전 시험에서 알람 비트 없음.
- 모든 구동 스크립트는 `finally`에서 `stop()` → `torque_off()` → `disable()`을 보장했다.
- 컨트롤러 설정 레지스터는 **하나도 쓰지 않았다.** 쓰기는 속도 지령과 `enable()`/`disable()`뿐이다.
- 최고 속도 1000 rpm은 `MAX_RPM=3200`의 31%. 100 → 250 → 500 → 750 → 1000 rpm으로
  3초씩 계단 상승 후 600 → 300 → 100 rpm으로 계단 하강했다.
- 자동 중단 조건: `status1` 비트 발생 / 지령 대비 실측 50% 미만이 1.5초 지속(스톨) / 통신 3회 연속 실패.
  이번 시험에서는 어느 것도 발동하지 않았다.
